# 总纲：只新增标书改写，保护现有全量编写

## 1. 现有链路与新增链路

### 1.1 现有全量编写

保持当前代码行为：

```text
InputManifest
→ SourceIndex
→ RequirementLedger
→ ScoreModel
→ ProjectModel
→ ChapterBlueprint
→ H1
→ ChapterWorkspace
→ 内部 ChapterWritingPlan
→ ChapterWritingService
→ WriterResearchCoordinator
→ ContentWriter
→ Content Gate
→ Draft / H2 / Word
```

### 1.2 新增标书改写

新增旁路：

```text
旧投标书上传
→ LegacyBidSourceManifest
→ LegacyBidIndex
                  ┐
新招标书走现有链路 ├→ 新目录 H1
                  ┘
注意：旧投标书不参与新目录生成

H1 后：
新叶子章节 + LegacyBidIndex
→ ChapterRewriteMatch
→ ChapterRewritePlan
→ 用户确认
→ BidRewriteExecutionService
→ ChapterWritingService
→ ContentWriter 或受控直接复用
→ Draft / H2 / Word
```

## 2. 目录规则

新目录必须只由以下内容生成：

- 新招标书；
- 新评分要求；
- 新补遗；
- 当前模板；
- 当前用户对新目录的反馈。

旧投标书目录不得作为新目录输入，也不得自动补充子目录。

原因很简单：用户要求的是“先根据新招标书生成简单目录，再按目录读取旧标书”。不能把顺序反过来，然后一本正经地称为融合。

## 3. 旧投标书独立存储

### 3.1 不进入主输入清单

新增：

```text
LegacyBidSourceManifest
LegacyBidIndex
```

旧标书原文件保存于：

```text
workspace/v3/legacy_bid_sources/<legacy_bid_id>/<filename>
```

主 `InputManifest` 和 `SourceIndex` 完全不登记旧标书。

### 3.2 复用解析器，不复用主索引

允许复用现有 DOCX/PDF/MD/TXT 结构解析代码，但输出进入 `LegacyBidIndex`。

建议为 `SourceNormalizer` 增加只读公共解析入口：

```python
parse_frozen_file(input_item, path)
```

现有 `normalize_active_inputs()` 仍只处理主 `InputManifest`。

### 3.3 LegacyBidIndex

至少包含：

```text
legacy_bid_id
filename
file_hash
parser_version
sections
blocks
structure_gaps
needs_review
```

`section`：

```text
section_id
parent_section_id
level
order
title
heading_block_id
content_block_ids
start_ordinal
end_ordinal
needs_review
```

`block` 保留：

```text
block_id
block_kind
ordinal
content
heading_path
page
paragraph_index
table_index
source_anchor
content_hash
```

## 4. 章节匹配

输入只能是：

- 当前新章节标题；
- Blueprint purpose；
- writing objectives；
- 当前章 requirement IDs；
- 当前章 score conditions；
- 当前内部 WritingPlan 的 blocks；
- LegacyBidIndex 的章节及段落。

步骤：

```text
标题/结构粗召回
→ 章节语义召回
→ 读取候选原始段落
→ 原文 rerank
→ 输出 exact block IDs/hash
```

不能只凭旧章节摘要最终选择，更不能把整本旧投标书塞给 Writer。

## 5. 改写策略

叶子章节支持四种内部策略：

```text
copy            直接复用
light_edit      修改复用
restructure     重组复用
new_write       重新编写
```

判断依据来自最终选中的旧段落和新要求覆盖情况，不能仅根据章节标题决定。

### 5.1 copy

- 旧内容完整覆盖新章要求；
- 结构无需实质调整；
- 没有未解决的旧项目污染；
- 不需要新增项目事实或公开资料。

### 5.2 light_edit

- 一个旧章节或连续段落为主体；
- 需要替换旧项目事实；
- 需要删除旧实体或补少量新内容；
- 主体结构不变。

### 5.3 restructure

- 多个旧章节或离散段落组合；
- 需要拆分、合并、重排；
- 多来源共同构成正文。

### 5.4 new_write

- 没有合适旧内容；
- 旧内容覆盖不足；
- 旧内容污染严重；
- 当前章主要依据新要求、当前项目资料和公开证据编写。

## 6. 污染治理

至少识别：

```text
旧项目名称
旧采购人/建设单位
旧地区
旧年份和日期
旧工期
旧人员
旧数量
旧型号/版本
旧标准版本
旧系统名称
旧合同承诺
```

处理方式：

```text
remove
replace_from_confirmed_fact
retain_as_generic_background
needs_human
```

没有新事实时不得自动猜测替换值。

## 7. 统一 Writer 规则

禁止新增：

```text
RewriteWriter
LegacyWriter
CopyWriter
```

新增的 `BidRewriteExecutionService` 只负责：

- 校验已确认的 `ChapterRewritePlan`；
- 装配旧段落快照；
- 决定执行策略；
- 创建现有 `ChapterWritingRequest`；
- 调用现有 `ChapterWritingService`。

### 7.1 直接复用

`copy` 可在 `ChapterWritingService` 内使用受控的 deterministic materializer 生成内容块，但仍必须经过：

```text
污染 Gate
内容 Gate
Draft commit
章节版本 CAS
```

### 7.2 其他策略

`light_edit/restructure/new_write` 仍调用现有 `ContentWriter`。

旧段落通过现有 `chapter_writing_plan` 的受控扩展字段进入冻结 Bundle，不新增第二个 Bundle 真相。

## 8. 全量编写保护规则

任何 PR 均必须证明：

- `full_write` 创建请求不传 mode 时行为不变；
- 原上传角色和材料就绪规则不变；
- 原目录候选不读取 LegacyBidIndex；
- 原章节工作台不出现“改写逻辑”；
- 原一键编写、聊天编写和批量编写调用不变；
- 原 Writer 仍执行当前联网判断；
- 原 Bundle 在无 rewrite plan 时不增加旧标书字段；
- 原 Word 导出结果不增加改写标签。

## 9. 每个 PR 的门禁

```bash
python -m compileall -q src

python -m pytest tests -q --tb=line -k "not live_llm"

cd frontend

```

除此之外，每个 PR 必须完成文档列出的真实页面验收。
