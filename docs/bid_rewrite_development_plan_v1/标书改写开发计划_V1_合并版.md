# 标书改写新增功能：START HERE

- 仓库：`breezePeak/bid_agent`
- 当前基线：`dbacba49b75aeb185091b12df44d1f08aa64fdc2`
- 计划版本：`Bid Rewrite Plan V1.0`
- 设计日期：`2026-08-24`
- 当前允许执行：**仅 PR-01**
- 原 `bid_agent_pr_development_plan_v2/unified_writing_pr_plan_v2`：**全部作废，不得继续执行**

## 1. 唯一产品目标

在现有“全量编写”功能保持原状的前提下，新增“标书改写”功能：

```text
新招标书 + 已完成的旧投标书
        ↓
只根据新招标书生成新的简单章节目录
        ↓
用户确认新目录
        ↓
按新目录逐章读取旧投标书
        ↓
判断当前章：
  直接复用 / 修改复用 / 重组复用 / 重新编写
        ↓
补齐新招标要求中旧标书没有覆盖的内容
        ↓
仍经现有 ChapterWritingService / ContentWriter 生成正文
```

## 2. 绝对边界

### 2.1 原有全量编写不改

以下现有行为必须保持：

- 新建普通工作空间仍默认进入全量编写；
- 原上传区、材料校验、解析、目录生成、H1、章节工作台、一键编写、批量编写、章节聊天、正文编辑、确认、Word 导出全部保持；
- 原 `ChapterWritingService` 仍是唯一公共章节写作入口；
- 原章节 WritingPlan、联网查询和 Writer 行为不因标书改写而切换；
- 不增加“全量编写 Plan v2”；
- 不要求原全量编写先确认新的章节规划；
- 不重做原搜索链路；
- 不修改原目录生成规则。

### 2.2 旧投标书走独立旁路

旧投标书必须满足：

- 不进入现有 `InputManifest`；
- 不进入现有 `SourceIndex`；
- 不进入 `RequirementLedger`；
- 不进入 `ScoreModel`；
- 不进入 `ProjectModel`；
- 不进入新目录生成输入；
- 不作为新项目事实；
- 只有新目录确认后，章节改写服务才可读取旧标书索引。

这条隔离是本计划最重要的设计。旧投标书一旦混进新项目理解，系统就会把旧项目名称、采购人、地区、年份和承诺当成新项目事实，随后整份标书开始考古。

## 3. 新功能的产品形态

### 项目级

新建工作空间时选择：

```text
○ 全量编写
○ 标书改写
```

- 旧工作空间和未传 `project_mode` 的请求：固定为 `full_write`。
- `bid_rewrite` 创建后不可随意切换为 `full_write`。

### 章节级

标书改写仍按章节执行：

```text
改写逻辑 | 正文
```

“改写逻辑”只在 `bid_rewrite` 工作空间显示。全量编写工作台不增加该页签。

## 4. 新 PR 顺序

```text
PR-01 改写项目入口、旧标书上传与解析预览
  ↓
PR-02 新招标书独立生成新目录，旧标书零污染
  ↓
PR-03 按新章节匹配旧章节/段落，只读改写逻辑
  ↓
PR-04 改写方案编辑、补充查询、确认与污染治理
  ↓
PR-05 单章改写执行，复用现有统一 Writer
  ↓
PR-06 批量改写、恢复、导出审计与真实验收
```

每个 PR 都必须同时有后端、前端、测试和人工可操作场景。禁止再出现“先写三轮后端，第四轮用户才看见页面”。

## 5. 现在怎么给 Codex

现在只给 Codex：

```text
CODEX_PR-01_启动提示词.md
```

不要同时发送 PR-02 至 PR-06，不要让它“顺便完成后续”。

PR-01 合并并通过人工验收前，不得开始 PR-02。

# 文件：01_总纲_只新增标书改写_保护全量编写.md

# 总纲：只新增标书改写，保护现有全量编写

## 1. 现有链路与新增链路

### 1.1 现有全量编写

保持当前代码行为：

```text
InputManifest
→ SourceIndex
→ RequirementLedger
→ ScoreModel
→ ProjectModel
→ ChapterBlueprint
→ H1
→ ChapterWorkspace
→ 内部 ChapterWritingPlan
→ ChapterWritingService
→ WriterResearchCoordinator
→ ContentWriter
→ Content Gate
→ Draft / H2 / Word
```

### 1.2 新增标书改写

新增旁路：

```text
旧投标书上传
→ LegacyBidSourceManifest
→ LegacyBidIndex
                  ┐
新招标书走现有链路 ├→ 新目录 H1
                  ┘
注意：旧投标书不参与新目录生成

H1 后：
新叶子章节 + LegacyBidIndex
→ ChapterRewriteMatch
→ ChapterRewritePlan
→ 用户确认
→ BidRewriteExecutionService
→ ChapterWritingService
→ ContentWriter 或受控直接复用
→ Draft / H2 / Word
```

## 2. 目录规则

新目录必须只由以下内容生成：

- 新招标书；
- 新评分要求；
- 新补遗；
- 当前模板；
- 当前用户对新目录的反馈。

旧投标书目录不得作为新目录输入，也不得自动补充子目录。

原因很简单：用户要求的是“先根据新招标书生成简单目录，再按目录读取旧标书”。不能把顺序反过来，然后一本正经地称为融合。

## 3. 旧投标书独立存储

### 3.1 不进入主输入清单

新增：

```text
LegacyBidSourceManifest
LegacyBidIndex
```

旧标书原文件保存于：

```text
workspace/v3/legacy_bid_sources/<legacy_bid_id>/<filename>
```

主 `InputManifest` 和 `SourceIndex` 完全不登记旧标书。

### 3.2 复用解析器，不复用主索引

允许复用现有 DOCX/PDF/MD/TXT 结构解析代码，但输出进入 `LegacyBidIndex`。

建议为 `SourceNormalizer` 增加只读公共解析入口：

```python
parse_frozen_file(input_item, path)
```

现有 `normalize_active_inputs()` 仍只处理主 `InputManifest`。

### 3.3 LegacyBidIndex

至少包含：

```text
legacy_bid_id
filename
file_hash
parser_version
sections
blocks
structure_gaps
needs_review
```

`section`：

```text
section_id
parent_section_id
level
order
title
heading_block_id
content_block_ids
start_ordinal
end_ordinal
needs_review
```

`block` 保留：

```text
block_id
block_kind
ordinal
content
heading_path
page
paragraph_index
table_index
source_anchor
content_hash
```

## 4. 章节匹配

输入只能是：

- 当前新章节标题；
- Blueprint purpose；
- writing objectives；
- 当前章 requirement IDs；
- 当前章 score conditions；
- 当前内部 WritingPlan 的 blocks；
- LegacyBidIndex 的章节及段落。

步骤：

```text
标题/结构粗召回
→ 章节语义召回
→ 读取候选原始段落
→ 原文 rerank
→ 输出 exact block IDs/hash
```

不能只凭旧章节摘要最终选择，更不能把整本旧投标书塞给 Writer。

## 5. 改写策略

叶子章节支持四种内部策略：

```text
copy            直接复用
light_edit      修改复用
restructure     重组复用
new_write       重新编写
```

判断依据来自最终选中的旧段落和新要求覆盖情况，不能仅根据章节标题决定。

### 5.1 copy

- 旧内容完整覆盖新章要求；
- 结构无需实质调整；
- 没有未解决的旧项目污染；
- 不需要新增项目事实或公开资料。

### 5.2 light_edit

- 一个旧章节或连续段落为主体；
- 需要替换旧项目事实；
- 需要删除旧实体或补少量新内容；
- 主体结构不变。

### 5.3 restructure

- 多个旧章节或离散段落组合；
- 需要拆分、合并、重排；
- 多来源共同构成正文。

### 5.4 new_write

- 没有合适旧内容；
- 旧内容覆盖不足；
- 旧内容污染严重；
- 当前章主要依据新要求、当前项目资料和公开证据编写。

## 6. 污染治理

至少识别：

```text
旧项目名称
旧采购人/建设单位
旧地区
旧年份和日期
旧工期
旧人员
旧数量
旧型号/版本
旧标准版本
旧系统名称
旧合同承诺
```

处理方式：

```text
remove
replace_from_confirmed_fact
retain_as_generic_background
needs_human
```

没有新事实时不得自动猜测替换值。

## 7. 统一 Writer 规则

禁止新增：

```text
RewriteWriter
LegacyWriter
CopyWriter
```

新增的 `BidRewriteExecutionService` 只负责：

- 校验已确认的 `ChapterRewritePlan`；
- 装配旧段落快照；
- 决定执行策略；
- 创建现有 `ChapterWritingRequest`；
- 调用现有 `ChapterWritingService`。

### 7.1 直接复用

`copy` 可在 `ChapterWritingService` 内使用受控的 deterministic materializer 生成内容块，但仍必须经过：

```text
污染 Gate
内容 Gate
Draft commit
章节版本 CAS
```

### 7.2 其他策略

`light_edit/restructure/new_write` 仍调用现有 `ContentWriter`。

旧段落通过现有 `chapter_writing_plan` 的受控扩展字段进入冻结 Bundle，不新增第二个 Bundle 真相。

## 8. 全量编写保护规则

任何 PR 均必须证明：

- `full_write` 创建请求不传 mode 时行为不变；
- 原上传角色和材料就绪规则不变；
- 原目录候选不读取 LegacyBidIndex；
- 原章节工作台不出现“改写逻辑”；
- 原一键编写、聊天编写和批量编写调用不变；
- 原 Writer 仍执行当前联网判断；
- 原 Bundle 在无 rewrite plan 时不增加旧标书字段；
- 原 Word 导出结果不增加改写标签。

## 9. 每个 PR 的门禁

```bash
python -m compileall -q src
ruff check src tests --quiet
python -m pytest tests -q --tb=line -k "not live_llm"

cd frontend
npm ci
npm test
npm run build
```

除此之外，每个 PR 必须完成文档列出的真实页面验收。

## 3. 后端实现

### 3.1 WorkspaceProfile


### 3.2 独立旧标书上传

新增专用接口：

```text
POST /api/v3/workspaces/{workspace_id}/legacy-bids
GET  /api/v3/workspaces/{workspace_id}/legacy-bids
```

# PR-05：单章改写执行，复用现有统一 Writer

## 1. 唯一目标

用户确认当前章节改写方案后，点击“开始改写”，系统按方案生成正文、流式显示、写入现有章节草稿，并继续使用当前正文编辑、确认和导出能力。

## 2. 禁止项

禁止新增：

```text
RewriteWriter
LegacyWriter
第二套章节写作 API
第二套草稿表
第二套正文编辑器
```

## 3. 执行服务

新增：

```text
BidRewriteExecutionService
bid_rewrite.chapter.execute
```

职责：

1. 校验 workspace 为 `bid_rewrite`；
2. 重载当前已确认 plan；
3. 校验 plan hash、依赖和章节 revision；
4. 加载 exact LegacyBid block snapshots；
5. 将改写方案装配为现有 `ChapterWritingRequest`；
6. 调用现有 `ChapterWritingService`；
7. 返回现有 draft revision。

## 4. 不新增 WriterInputBundle 真相

利用现有：

```text
ChapterWritingRequest.chapter_writing_plan
WriterInputBundle.chapter_writing_plan
```

增加受控 rewrite 字段：

```json
{
  "rewrite_schema": "v1",
  "rewrite_strategy": "light_edit",
  "selected_legacy_sources": [],
  "new_content_items": [],
  "selected_evidence_refs": [],
  "replacement_map": [],
  "pollution_receipt": {}
}
```

`ChapterWritingKernel` 仅在该字段存在时把 rewrite context 放入 prompt。普通全量编写的 payload 和 prompt 不增加空字段。

## 5. 四种执行方式

### copy

```text
exact selected blocks
→ confirmed replacement map
→ 格式标准化
→ LegacyPollutionGate
→ WriterBundleContentGate
→ chapter.generate_draft
```

直接复用不调用模型改写，但仍通过同一个 `ChapterWritingService` 编排和现有草稿提交。

### light_edit

现有 ContentWriter 读取：

- 旧主体；
- 替换映射；
- 新要求缺口；
- 项目事实；
- 已选证据。

### restructure

现有 ContentWriter 按新 WritingPlan blocks 重排多个旧来源。

### new_write

现有 ContentWriter 按当前全量章节写作逻辑编写，但只使用已确认的当前章来源。

## 6. 查询规则

改写方案确认后：

```text
run_research = False
```

正文阶段不再添加新来源。

缺少必要资料时，在 PR-04 阶段解决；否则执行返回明确的 `REWRITE_PLAN_INCOMPLETE`。
