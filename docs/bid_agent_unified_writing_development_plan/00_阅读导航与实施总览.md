# 标书 Agent：统一章节编写规划与标书改写功能开发计划

- 计划基线：`breezePeak/bid_agent`
- 基线分支：`main`
- 基线提交：`74cd1ff12a79a373f9c262d48f61e03caa3cd642`
- 生成日期：`2026-08-21`
- 适用范围：当前 V3 主架构，不恢复 V1/V2，不新增第二套 Writer
- 文档目标：把“全量编写”和“标书改写”统一到同一条章节规划、确认、写作、编辑和晋级链路中，并通过分阶段门禁保证现有功能不被破坏

---

## 1. 先看结论

本次开发不是增加一个孤立的“旧标书改写页面”，而是在当前架构中补上一层正式的章节级权威对象：

```text
当前链路
ChapterBlueprint
    → 聊天区 writing_outline
    → WriterInputBundle
    → ChapterWritingService
    → ContentWriter

目标链路
ChapterBlueprint
    → ChapterWritingPlan
    → 用户/代审确认
    → WriterInputBundle
    → ChapterWritingService
    → ContentWriter
```

两种项目模式只在“规划阶段可用的素材池”不同：

| 素材 | 全量编写 | 标书改写 |
|---|---:|---:|
| 新招标书要求 | 使用 | 使用 |
| 评分要求 | 使用 | 使用 |
| 全局项目事实 | 使用 | 使用 |
| 章节上下文与用户资料 | 使用 | 使用 |
| 旧投标书目录结构 | 不使用 | 生成新目录时参考 |
| 旧投标书正文段落 | 不使用 | 章节规划时按段落选择 |
| 公开搜索资料 | 按需 | 按需 |
| 用户临时补充资料 | 使用 | 使用 |

正文仍然由当前唯一的 `ChapterWritingService → ContentWriter` 生成。  
不会出现 `RewriteWriter`、`FullWriter`、`RewriteWorkbench` 这类第二套链路。工程一旦开始复制两套流程，后面通常只剩下开发者轮流猜哪一套才是真的。

## 3. 总体实施顺序

```text
PR0  冻结基线并补齐当前行为特征测试
 ↓
PR1  增加 writing_mode、LEGACY_BID 等增量契约，默认关闭新行为
 ↓
PR2  建立 ChapterWritingPlan 控制面、版本、哈希、确认回执和 CAS
 ↓
PR3  在全量编写模式下“影子生成”章节规划，不影响现有 Writer
 ↓
PR4  上线中间区域“编写逻辑/正文”双页签，先只读展示
 ↓
PR5  开放规划修改、确认，Writer 精确消费已确认来源
 ↓
PR6  全量编写新链路小范围启用，保留旧链路回退
 ↓
PR7  增加旧投标书角色、结构恢复、LegacyBidIndex 和 Markdown 投影
 ↓
PR8  新招标要求与旧目录结构融合生成新目录
 ↓
PR9  旧段落匹配、搜索补充、四类改写、规划图和逐章编写
 ↓
PR10 批量编写、陈旧传播、导出标签隔离、并发和断点恢复
 ↓
PR11 故障注入、性能优化、可观测性和真实标书黄金样本评估
 ↓
PR12 灰度发布、旧工作空间兼容验证和正式切换
```

任何一个阶段未通过本阶段门禁，不得开始下一阶段。  
这不是为了让流程显得庄严，而是为了避免“数据库还没迁完，前端已经开始调用不存在的字段”这种十分常见、又十分没必要的表演。

## 4. 五条最高优先级不变量

### 4.1 现有 V3 架构权威不变

- `ChapterBlueprint` 仍是章节结构、职责和评分归属的唯一权威。
- `WriterInputBundle` 仍是 Writer 唯一合法输入。
- `ChapterWritingService` 仍是章节正文生成的唯一服务入口。
- Writer 不能联网、不能直接读取工作空间、不能写控制库。
- Agent 只能产出提案、计划候选、Issue 或 Finding，不能直接切换 canonical 状态。

### 4.2 新功能默认不影响旧工作空间

- 数据库只做增量迁移，不删除旧列、不重写旧内容。
- 缺少 `writing_mode` 的旧工作空间按现有全量编写兼容模式运行。
- Feature Flag 关闭时，现有聊天提纲和写作链路保持原样。
- 新的“规划确认后才能写作”规则，只对明确启用新能力的工作空间生效。

### 4.3 搜索必须在规划确认前完成

- 用户在“编写逻辑”页看到最终将使用的来源。
- 搜索结果必须抓取并保存原文快照；搜索摘要只能用于候选筛选，不能直接代替原文。
- 规划确认后 Writer 不得继续偷偷搜索。
- 写作中发现资料不足时，返回 `CHAPTER_PLAN_REVISION_REQUIRED`，回到规划阶段补材料。

### 4.4 旧投标书只能作为结构与素材来源

- 新招标书、评分标准和新项目事实决定“必须写什么”。
- 旧投标书目录决定“过去如何展开”，只能作为候选结构。
- 旧投标书正文决定“哪些内容可复用”，不能自动进入新项目全局事实。
- 旧项目名称、年份、地点、人员、参数、标准版本必须经过污染检查。

### 4.5 用户确认必须绑定精确版本

章节规划确认至少绑定：

```text
chapter_id
plan_revision
plan_hash
blueprint_revision + blueprint_hash
chapter_context_revision + hash
global_context_revision + hash
selected SourceBlock IDs + content_hash
selected EvidenceItem IDs + snapshot_hash
reviewer
confirmation mode
dependency_fingerprint
```

任何一个依赖变化，原确认不能继续冒充有效。所谓“确认过一次以后一直算确认”，是最便宜也最危险的状态管理。

## 5. 本计划如何避免“走一步报一堆错误”

本计划不能神奇地消灭所有缺陷，但会用工程门禁阻止缺陷跨阶段扩散：

1. **先补特征测试，再改行为**：先锁住当前全量编写、聊天、批量写作、导出和确认流程。
2. **契约先行**：先增加 Schema、数据库和 API 返回字段，再改调用方。
3. **默认关闭**：新代码先在 Feature Flag 后运行，不立即替换现有路径。
4. **影子运行**：先生成规划但不影响 Writer，对比新旧输出和耗时。
5. **双读单写**：过渡期读取新旧状态，写入仍由一个权威服务完成。
6. **精确回滚**：关闭 Flag 即回到现有链路，增量表和字段保留，不做逆向删表。
7. **每个 PR 可独立部署**：不允许一个 PR 依赖“下一个 PR 才会补上的接口”。
8. **真实工作空间迁移演练**：对现有 `runs/<workspace>` 副本执行迁移、打开、写作、导出和回滚。
9. **故障注入**：主动模拟 LLM 非法 JSON、搜索超时、SQLite 锁、浏览器断线和服务重启。
10. **最终以业务场景验收**：不只看单元测试通过，还要完成一套全量编写和一套标书改写的完整闭环。

## 6. 最终交付形态

开发完成后，用户看到的工作台核心行为应为：

```text
选择章节
  ↓
中间默认打开“编写逻辑”
  ↓
章节 Agent 生成来源 → 内容块 → 目标章节的规划
  ↓
用户查看、增删来源、继续搜索、调整内容块
  ↓
用户确认精确规划版本
  ↓
点击“开始编写”
  ↓
统一 Writer 只使用已确认材料生成正文
  ↓
中间自动切换到“正文”
  ↓
用户编辑、重新生成、确认章节
```

标书改写模式下，章节标题后显示：

```text
【全部搬用】
【简单修改】
【理解重组】
【重新编写】
```

父章节存在多种子类型时显示：

```text
【混合处理】
```

这些标签仅为工作台元数据，最终 Word、PDF、正式 Markdown 和目录导出绝不能包含它们。
