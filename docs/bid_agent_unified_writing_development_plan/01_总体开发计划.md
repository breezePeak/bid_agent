# 总体开发计划

## 1. 项目名称

**标书 Agent V3：统一章节编写规划与标书改写能力建设**

基线：`main@74cd1ff12a79a373f9c262d48f61e03caa3cd642`

---

## 2. 建设目标

本项目建设两个表面上不同、底层完全统一的写作模式：

### 2.1 全量编写

用户上传新招标文件、评分标准、模板和项目资料。系统生成并确认全局目录后，用户逐章进入工作台：

1. 章节 Agent 分析本章要求；
2. 判断已有材料是否充分；
3. 必要时在规划阶段搜索并抓取原文；
4. 生成可视化编写规划；
5. 用户确认规划；
6. 用户点击“开始编写”；
7. 统一 Writer 生成正文；
8. 用户编辑并确认章节。

### 2.2 标书改写

用户上传新招标书和旧投标书。系统：

1. 解析新招标要求和评分点；
2. 恢复旧投标书完整目录树和段落；
3. 对旧章节、旧段落生成语义描述；
4. 用新招标要求确定内容边界，用旧目录提供拆分颗粒度；
5. 生成可修改、可确认的新目录；
6. 进入同一工作台；
7. 每章显示将使用的旧章节、旧段落、项目资料和搜索材料；
8. 用户确认后逐章编写；
9. 根据最终规划动态标注“全部搬用、简单修改、理解重组、重新编写”。

### 2.3 统一目标

两种模式必须共用：

- 同一个 `ChapterBlueprint`；
- 同一个 `ChapterWritingPlan`；
- 同一个章节工作台；
- 同一个确认模型；
- 同一个 `WriterInputBundle`；
- 同一个 `ChapterWritingService`；
- 同一个正文编辑、版本、确认和导出链路。

---

## 3. 非目标

本次开发明确不做以下事情：

1. 不恢复或兼容已经移除的 V1/V2 写作链路。
2. 不新建第二套 Writer、第二套章节状态或第二个工作台。
3. 不把旧投标书全文直接塞进模型上下文。
4. 不允许搜索摘要直接作为正文唯一依据。
5. 不允许旧投标书自动更新新项目的全局事实。
6. 不在最终导出文档中显示改写类型标签。
7. 不用标题文本相似度代替稳定 ID、来源哈希和依赖指纹。
8. 不在本次改造中顺手大拆 `control_plane.py` 或 `ChapterWorkbenchView.vue`；必要拆分要以行为不变的独立 PR 进行。
9. 不在第一版规划图中引入重型图编辑器；固定三列关系用 CSS Grid 与 SVG 即可。
10. 不在同一个 PR 同时完成数据库迁移、旧标书解析、Writer 切换和 UI 上线。

## 4. 当前架构中的保留核心

| 当前核心 | 本次处理 |
|---|---|
| `ChapterBlueprint` | 保留为目录、章节职责和评分归属权威；增加旧目录来源追踪字段 |
| `chapter_writing_outline.py` | 保留并升级为规划中的 `content_units` |
| `ChapterWritingService` | 保留为正文生成唯一入口；改为校验已确认规划并禁止规划后搜索 |
| `WriterInputBundleAssembler` | 保留；增加精确规划快照和精确来源白名单 |
| `ContentWriter` | 保留；不获得联网、数据库或任意文件权限 |
| `ChapterWorkspaceService` | 保留；增加规划摘要、计划 revision 和陈旧状态 |
| `ChapterAgentService` | 保留聊天和意图理解；不再持有正式规划权威 |
| `ControlStore` | 保留；增加章节规划追加版本、确认回执和 CAS |
| `ArtifactPromotionService` | 保留全局 Artifact 晋级；新增 `LegacyBidIndex` 注册 |
| 全局 H1 目录确认 | 保留且仍只确认一次；章节规划确认不是第二次全局 H1 |
| 章节正文版本/确认 | 保留并与规划 revision 绑定 |
| 批量编写 | 保留；新模式下只允许已确认且未陈旧的章节进入队列 |
| Word/PDF/Markdown 导出 | 保留；过滤 UI 改写标签 |

## 6. 工作分解结构

### 工作流 A：基线保护与兼容层

交付：

- 当前行为特征测试；
- 真实工作空间样本；
- Feature Flag；
- 旧工作空间能力判定；
- 兼容模式；
- 数据库备份和迁移演练工具。

### 工作流 B：章节编写规划内核

交付：

- `ChapterWritingPlan` Schema；
- 计划提案、验证、晋级和确认回执；
- 计划追加版本；
- 来源、内容块、绑定关系；
- 计划哈希、依赖指纹和陈旧传播；
- 计划 API 与事件流。

### 工作流 C：全量编写统一改造

交付：

- 搜索从 Writer 阶段前移到规划阶段；
- 规划页展示项目资料和搜索来源；
- 用户确认后 Writer 精确消费；
- 写作时不再新增来源；
- 原全量编写行为兼容开关。

### 工作流 D：旧投标书结构化

交付：

- `InputRole.LEGACY_BID`；
- 目录树恢复；
- 章节和段落语义描述；
- `LegacyBidIndex`；
- 旧项目实体风险；
- Markdown 只读投影；
- 多旧标书支持。

### 工作流 E：新旧目录融合

交付：

- 新要求节点；
- 旧目录子树候选；
- 保留、改名、合并、拆分、删除和新增；
- `outline_lineage`；
- 用户修改后沿用现有 H1 确认。

### 工作流 F：前端工作台

交付：

- “编写逻辑 / 正文”双页签；
- 三列规划图；
- 来源详情与原文预览；
- 继续搜索；
- 规划编辑与确认；
- 结构化“开始编写”；
- 类型标签；
- 陈旧和失败恢复。

### 工作流 G：质量、发布和运维

交付：

- 回归矩阵；
- 故障注入；
- 黄金标书评估；
- 性能预算；
- 日志、指标和诊断包；
- 灰度、回滚和事故手册。

## 7. 里程碑

### M0：基线冻结

完成标准：

- 所有当前 CI 命令通过；
- 固化 3 类工作空间样本；
- 当前章节聊天、单章写作、批量写作、章节确认和导出均有自动化特征测试；
- 形成“不可破坏行为清单”。

### M1：规划内核可用，但不改变现有行为

完成标准：

- 数据库可保存计划版本；
- 计划哈希和依赖指纹稳定；
- 计划确认支持 CAS、幂等和重放拒绝；
- Feature Flag 关闭时全套旧测试仍通过；
- UI 尚未启用也不影响当前工作流。

### M2：全量编写影子规划

完成标准：

- 章节规划可生成；
- 能展示招标、评分、项目资料和搜索来源；
- 规划只影子记录，不阻止当前写作；
- 新旧搜索结果对比可观测；
- 无新增线上错误。

### M3：全量编写新链路小范围启用

完成标准：

- 用户能修改并确认规划；
- Writer 只收到确认来源；
- 规划确认后不再搜索；
- 规划变化使旧草稿陈旧但不删除；
- 单章、批量、重新生成、确认和导出通过回归。

### M4：旧投标书解析和目录融合

完成标准：

- 旧投标书目录与段落覆盖率达标；
- 每个语义描述可追溯到 canonical `block_id`；
- 新目录能参考旧目录下级结构；
- 新招标约束仍保持主权；
- 严格模板模式不被旧目录破坏。

### M5：标书改写完整闭环

完成标准：

- 新旧文件上传；
- 融合目录确认；
- 每章规划图；
- 旧段落、项目资料和 Web 来源共同绑定；
- 四种改写类型准确计算；
- 逐章生成、编辑、确认和导出全部完成。

### M6：正式发布

完成标准：

- 灰度工作空间无 P0/P1；
- 现有旧工作空间通过兼容回归；
- 性能达到预算；
- 回滚演练通过；
- 运维和故障诊断文档齐全。

## 8. 关键依赖关系

```text
数据库增量迁移
    └─> ChapterWritingPlan 存储
          └─> 规划 API
                └─> 前端规划页
                      └─> Writer 强制消费确认规划

InputRole.LEGACY_BID
    └─> SourceIndex 中旧标书块
          └─> LegacyBidIndex
                ├─> 新旧目录融合
                └─> 章节旧段落候选
                      └─> 改写类型计算
                            └─> 标书改写完整工作台
```

不允许倒序。例如在 `LegacyBidIndex` 还没有稳定 ID 和覆盖门禁之前，不能先做旧段落规划图；否则前端会绑定临时索引，随后一重解析，所有连线集体失忆。

## 9. 总体风险登记

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 新计划状态与 `_authority.json` 冲突 | 同一章节出现两个确认结果 | 新规划启用后 `_authority.json` 只保存权限模式；正式 plan status 只读控制库 |
| 规划确认后 Writer 又执行搜索 | 用户确认失真 | 新能力工作空间强制 `run_research=False`；传 true 直接报错 |
| 旧标书污染新项目事实 | 错项目名、年份、地点进入正文 | 旧材料单独角色；实体风险标注；Writer 前后双重污染门 |
| 旧目录压过新招标要求 | 目录好看但漏评分项 | ScoreResponseUnit 主责唯一性和现有 Blueprint Gate 不变 |
| 计划改动后旧正文仍标有效 | 用户误用过期内容 | plan revision 进入 draft dependency；变化后设置 `DRAFT_STALE` |
| 数据库迁移中断 | 工作空间打不开 | 增量 DDL、事务、幂等迁移、备份、副本演练 |
| 前端大组件继续膨胀 | 维护困难、回归面大 | 新逻辑拆成独立组件和 composable，不在工作台内堆一万行 |
| 多章节批量绕过确认 | 未审核规划直接写作 | 前后端双重门禁；批量队列保存 plan revision/hash |
| 搜索只拿摘要 | 正文空泛、引用不可靠 | 原文获取状态为 ready 才可确认并进入 Writer |
| 多旧标书候选混乱 | 来源重复或互相冲突 | 文档优先级、候选去重、每条 binding 明确 source_input_id |
| LLM 输出非法结构 | 流程卡死 | Pydantic 严格 Schema、分批、重试、确定性降级、保留失败诊断 |
| Feature Flag 组合爆炸 | 难以测试 | 只保留三层能力标志，明确定义允许组合，禁止任意交叉 |

## 10. 资源与角色建议

即便只有一个开发者，也按角色分工审查：

| 角色 | 责任 |
|---|---|
| 架构负责人 | 守住 Blueprint、Bundle、Writer 权限和 Promotion 边界 |
| 后端负责人 | Schema、控制库、服务、API、错误恢复 |
| 前端负责人 | 双页签、规划图、交互、状态与兼容 |
| 质量负责人 | 特征测试、回归矩阵、故障注入、黄金样本 |

同一人可以戴五顶帽子，只是提交前要分别检查，别让“我写的我当然觉得没问题”成为唯一质量门。

## 11. 总体验收指标

### 功能正确性

- 两种模式均能完成完整项目闭环。
- 每章必须先有确认规划，才能进入新链路 Writer。
- 旧段落和 Web 来源均能追溯到原始内容。
- 四类改写标签与最终来源绑定一致。
- 父节点混合类型只在 UI 汇总，不污染叶子策略。
- 最终导出无内部标签和内部来源元数据。

### 架构正确性

- Writer 无外部工具权限。
- Agent 无 canonical 写权限。
- 所有确认都绑定精确 hash 和 revision。
- 陈旧版本被拒绝。
- 章节之间上下文隔离不被破坏。
- 全局 H1 确认仍然只有一次。

### 兼容性

- Flag 全关时行为与基线一致。
- 旧工作空间无需手工迁移即可打开、编辑、写作和导出。
- 现有 API 客户端在不发送新字段时仍可运行。
- 现有所有确定性测试通过。

### 性能

建议第一版预算：

| 操作 | 目标 |
|---|---:|
| 加载章节基础信息 | P95 < 1.5 秒 |
| 加载已存在规划 | P95 < 1 秒 |
| 规划图 100 个节点首屏渲染 | < 500 毫秒 |
| 规划确认事务 | P95 < 500 毫秒 |
| 旧标书 5000 段索引查询 | P95 < 1 秒 |
| 页面切换章节 | 不阻塞正文编辑，失败可局部重试 |
| 断线重连 | 不重复提交确认或生成任务 |

## 12. 开发完成后的标准业务流程

```text
创建项目
  ├─ 全量编写
  └─ 标书改写

上传输入
  ↓
材料解析与 Artifact 晋级
  ↓
生成目录候选
  ├─ 全量编写：新招标 + 评分 + 模板
  └─ 标书改写：上述内容 + 旧目录候选结构
  ↓
用户修改并完成现有 H1 目录确认
  ↓
章节工作空间初始化
  ↓
用户逐章进入“编写逻辑”
  ↓
生成、调整并确认 ChapterWritingPlan
  ↓
结构化点击“开始编写”
  ↓
统一 Writer 生成正文
  ↓
用户编辑、确认
  ↓
文档组装、质量检查和导出
```
