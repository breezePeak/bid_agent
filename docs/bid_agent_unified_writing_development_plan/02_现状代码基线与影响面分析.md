## 3. 当前真实章节写作链路

### 3.1 前端入口

当前章节工作台的“开始编写”最终会通过章节聊天链路表达用户意图。前端现有 API 支持：

- `fetchChapter(...)`
- `fetchChapterChatHistory(...)`
- `fetchChapterChatAuthority(...)`
- `saveChapterChatAuthority(...)`
- `streamChapterChat(...)`
- `streamChapterDraft(...)`
- `fetchChapterRevisions(...)`
- 章节批量任务相关接口

现有 `streamChapterChat` 请求体只有：

```json
{
  "message": "开始编写本章正文"
}
```

按钮操作仍然作为自然语言进入 Agent，再由 Agent 判断这是“回答问题、列提纲、确认提纲还是写正文”。

### 3.2 章节详情加载

`GET /api/v3/workspaces/{workspace_id}/chapters/{chapter_id}` 会组装：

- 章节基础信息；
- 全局项目上下文引用；
- 章节上下文引用；
- 本章招标要求；
- 本章评分要求；
- 兄弟章节只读上下文；
- 全文目录上下文；
- `WritingOrientation`；
- `compile_chapter_writing_outline(...)` 生成的 `writing_outline`。

当前 `writing_outline` 是一个 Service 投影，不是 canonical Artifact，也没有正式章节级确认回执。

### 3.3 聊天提纲审核

`chapter_chat.py` 当前将权限和提纲审核信息保存到：

```text
workspace/v3/chapter_chats/_authority.json
```

主要字段：

```text
default_mode
chapter.mode
review_status
outline_hash
base_outline_hash
outline_snapshot
```

支持权限模式：

```text
human_review
delegate_review
full_authority
```

`resolve_write_phase(...)` 根据自然语言动作、当前模式和 `outline_hash` 判断：

```text
respond_only
list_for_review
write_body
```

### 3.4 正文生成

`ChapterWritingService.write()` 当前顺序：

```text
_validate_request
_validate_outline_authority
WriterInputBundleAssembler.assemble
WriterResearchCoordinator.prepare
ContentWriter
Grounding / Content Gate
append chapter content revision
```

`iter_events()` 会在正文前发出研究事件，然后进入 drafting。

这意味着当前搜索发生在 Writer 调用前的同一个“写正文操作”中，而不是一个可由用户查看和确认的独立规划阶段。

### 3.5 当前 Writer 输入

现有 `WriterInputBundle` 包含：

- `blueprint_slice`
- `requirement_excerpts`
- `score_obligations`
- `evidence_snapshot`
- `research_decisions`
- `global_project_context`
- `chapter_context`
- `existing_content`
- `target_output`
- `allowed_source_ids`
- `dependency_fingerprint`

但缺少：

- 已确认的章节规划 revision/hash；
- 规划确认回执；
- 来源与内容块绑定；
- 精确选择的旧投标书段落；
- 用户删除来源后的排除信息；
- 规划到正文的精确追溯。

## 4. 当前全局目录生成链路

### 4.1 当前输入

`OutlineDecompositionInput` 当前只有：

```python
requirement_ledger
score_model
template_structure
document_mode
review_feedback
```

其中 `document_mode` 仅表示：

```text
auto_outline
template_strict
```

它不是“全量编写 / 标书改写”。

### 4.2 当前提示词约束

`prompts/v3_planning_agent_blueprint.md` 明确要求输入只包含：

- `RequirementLedger`
- `ScoreModel`
- 可选 `TemplateStructureContract`

因此当前目录模型在设计上看不到旧投标书目录。它无法利用旧标书中：

```text
项目任务背景
  ├─ 年度任务变化
  ├─ 平台支撑
  └─ 国家级核查背景
```

这类成熟下级结构。要实现新旧目录融合，必须改全局 planning input、prompt、validator 和 Blueprint lineage，不是只改章节 Agent。

## 5. 当前输入与 Source 权威

### 5.1 InputRole

当前角色：

```text
tender
score
template
amendment
company
reference
guidance
```

缺少：

```text
legacy_bid
```

旧投标书不能冒充 `company`，也不应混入普通 `reference`。它需要独立业务规则、结构解析、复用和污染检查。

### 5.2 SourceBlock

现有 `SourceBlock` 已经具备稳定来源身份：

```text
block_id
input_id
input_role
block_kind
ordinal
content
heading_path
page
paragraph_index
table_index
row_index
column_index
reading_order
source_anchor
content_hash
```

因此没有必要另造一套“旧标书段落 ID”。  
所有旧章节和段落索引都必须反向绑定 canonical `block_id`。Markdown 文件只是可读投影，不能成为 Writer 的权威输入。

## 7. 当前工作空间创建缺口

前端 `createRun(name, projectType, expectedPages)` 会提交：

```json
{
  "name": "...",
  "project_type": "...",
  "expected_pages": 100
}
```

当前后端 `POST /api/v3/workspaces` 只读取 `name` 并创建目录、控制库和 ACL，没有保存 `project_type` 与 `expected_pages`。

本次不能再在前端多加一个 `writing_mode` 然后继续让后端礼貌性忽略。必须：

1. 明确创建请求 Schema；
2. 在控制库持久化；
3. 快照与列表接口返回；
4. 前端重载后仍能恢复；
5. 旧请求缺少字段时默认 `full_write`。

## 8. 当前 Artifact Registry 约束

`artifact_registry.py` 是严格白名单。当前可晋级类型包括：

```text
InputManifest
SourceIndex
TemplateStructureContract
RequirementLedger
ScoreModel
ProjectModel
ResponseTopicGraph
ChapterBlueprint
```

新增 `LegacyBidIndex` 后必须：

- 定义严格 Pydantic Schema；
- 注册合法 producer；
- 声明依赖 `SourceIndex`；
- 配置 Gate；
- 增加 Promotion、重放、陈旧和非法 producer 测试；
- 提升 Registry version。

否则旧标书索引只会成为一份旁路 JSON，绕开当前最重要的保护内核。

## 11. 绝对不能直接修改的边界

### 11.1 不让 Agent 直接写控制库

Agent 只返回：

```text
ChapterWritingPlanProposal
LegacyDescriptionProposal
OutlineCandidate
Issue/Finding
```

由 Service 验证并写入。

### 11.2 不让 Writer 读取旧标书文件路径

Writer 只能收到服务冻结的：

```text
selected_source_blocks
selected_evidence_snapshots
confirmed_plan_snapshot
```

### 11.3 不把章节规划塞进 Blueprint

Blueprint 管：

```text
章节是什么
为什么存在
负责哪些评分项和要求
```

ChapterWritingPlan 管：

```text
本次准备使用什么材料
材料写到哪个内容块
如何写
```

二者 revision 和职责必须分开。

### 11.4 不把正式规划继续塞进 `_authority.json`

该文件最多保留：

```text
default_mode
chapter mode
```

正式 plan revision、hash、状态和回执进入控制库。

### 11.5 不立即删除旧写作路径

至少经历：

```text
影子运行
→ 新工作空间 opt-in
→ 灰度
→ 默认开启
→ 两个发布周期稳定
```

之后再单独评估旧路径清理。

## 12. 需要先补的特征测试

在新增功能前，至少锁住以下当前行为：

1. 创建旧式工作空间请求缺少新字段仍成功。
2. 上传现有所有 InputRole 正常。
3. 自动目录与严格模板目录均可生成、确认。
4. 章节工作空间按 Blueprint 正确 materialize。
5. 章节聊天历史隔离。
6. human/delegate/full authority 三种模式行为。
7. 现有提纲确认后可写正文。
8. 当前 Writer research 事件顺序。
9. 单章流式正文失败后不产生半个正式 revision。
10. 批量任务创建、暂停、恢复、重启恢复。
11. 章节上下文修改只影响当前章节。
12. 正文版本、撤回、确认、正式 revision。
13. Word/PDF/Markdown 导出。
14. 旧工作空间打开快照。
15. Feature Flag 全关时上述行为完全不变。

这些特征测试不是歌颂现有实现，而是给改造划地界。没有它们，开发者每改一处都只能靠记忆判断“以前是不是这样”，那基本等于没有判断。
