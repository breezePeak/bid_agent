# 目标产品流程、状态机与业务规则

## 1. 项目级入口

创建项目时增加独立字段：

```text
writing_mode:
- full_write
- bid_rewrite
```

现有：

```text
document_mode:
- auto_outline
- template_strict
```

继续保留。两者是两个维度：

| writing_mode | document_mode | 含义 |
|---|---|---|
| full_write | auto_outline | 根据新招标和评分生成目录，全量写作 |
| full_write | template_strict | 严格按模板目录，全量写作 |
| bid_rewrite | auto_outline | 新招标内容权威 + 旧目录结构参考 |
| bid_rewrite | template_strict | 模板结构权威，旧目录只可辅助 slot 内拆分与正文来源 |

---

## 2. 全量编写完整流程

```text
创建 full_write 项目
  ↓
上传招标书、评分、模板、公司/项目资料
  ↓
SourceIndex / RequirementLedger / ScoreModel / ProjectModel
  ↓
生成 ChapterBlueprint 候选
  ↓
用户修改并完成现有 H1 确认
  ↓
materialize 章节工作空间
  ↓
用户点开某章
  ↓
默认进入“编写逻辑”
  ↓
读取本章约束、全局事实、章节上下文和已有材料
  ↓
判断资料缺口
  ├─ 无缺口：直接生成规划候选
  └─ 有缺口：规划阶段搜索、获取原文、生成证据快照
  ↓
生成 sources / content_units / bindings
  ↓
用户增删来源、调整内容块、继续搜索
  ↓
确认 ChapterWritingPlan 精确版本
  ↓
用户点击“开始编写”
  ↓
Writer 只消费已确认规划
  ↓
生成 ChapterContentRevision 草稿
  ↓
正文编辑、局部重写、整章重写、确认
  ↓
最终组装和导出
```

全量编写“编写逻辑”页必须显示：

- 本章招标要求；
- 本章评分项和满分条件；
- 全局项目事实；
- 章节上下文；
- 用户上传资料；
- 已抓取的 Web 原文来源；
- 每份材料计划支持哪个内容块；
- 材料状态和风险。

不能只显示搜索来源。否则系统会把用户上传的项目资料当空气，然后兴致勃勃地去互联网上找不一定相关的东西，颇具人类会议的风范。

## 3. 标书改写完整流程

### 3.1 材料阶段

```text
创建 bid_rewrite 项目
  ↓
上传新招标书
  ↓
上传一份或多份旧投标书（legacy_bid）
  ↓
解析全部文件为 SourceIndex
  ↓
新文件进入现有 Requirement/Score/Project 解析
  ↓
旧投标书进入 LegacyBidIndex 派生与晋级
```

### 3.2 旧投标书结构化

每份旧投标书生成：

- 完整目录树；
- 标题块和章节边界；
- 段落归属；
- 每个章节语义描述；
- 每个段落语义描述；
- 内容类型；
- 回答的问题；
- 可复用条件；
- 旧项目实体风险；
- canonical `block_id`；
- Markdown 只读投影。

### 3.3 新旧目录融合

```text
新招标要求/评分
决定“必须覆盖什么”
        +
旧投标书目录树
提供“可以怎样拆开写”
        +
模板结构
决定“是否允许改层级”
        ↓
生成 ChapterBlueprint 候选
```

大模型对旧目录节点只能做：

```text
reused
adapted
merged
split
ignored
```

同时允许根据新招标要求新增节点。

用户在现有 H1 目录确认页面中：

- 修改标题；
- 增删章节；
- 调整层级和顺序；
- 查看旧目录来源；
- 查看对应评分和招标要求；
- 最终完成一次全局 H1 确认。

### 3.4 章节工作台

进入工作台后不批量预写正文。

```text
用户点开章节
  ↓
默认进入“编写逻辑”
  ↓
显示旧投标书候选段落、项目资料和搜索来源
  ↓
形成来源 → 内容块 → 新章节关系
  ↓
用户确认规划
  ↓
逐章点击“开始编写”
  ↓
统一 Writer 生成正文
```

## 4. 中间区域统一交互

中间区域固定两个页签：

```text
[编写逻辑] [正文]
```

### 4.1 默认页签规则

| 条件 | 默认页签 |
|---|---|
| 没有正文 | 编写逻辑 |
| 规划正在生成 | 编写逻辑 |
| 规划待确认 | 编写逻辑 |
| 规划已确认但未写 | 编写逻辑 |
| 已有有效草稿 | 正文 |
| 规划已陈旧、正文仍存在 | 正文，但顶部强提醒并可切换编写逻辑 |
| 正文生成中 | 正文，显示流式进度 |
| 规划生成失败 | 编写逻辑，显示局部错误与重试 |

### 4.2 编写逻辑页

统一三列：

```text
来源材料            计划内容块            当前章节
```

来源材料可以是：

- 招标要求；
- 评分义务；
- 全局项目事实；
- 章节上下文；
- 用户上传资料；
- 旧投标书段落；
- Web 原文证据；
- 用户临时备注。

连接线显示：

```text
主体内容
补充事实
结构参考
用于举证
只用于背景
替换项目信息
合并后重组
禁止使用
```

### 4.3 正文页

保持现有编辑能力：

- 实时修改；
- 删除内容块；
- 局部重新生成；
- 整章重新生成；
- 版本查看；
- 撤回；
- 确认；
- 展示来源追溯；
- 不跨章节修改其他正文。

## 5. 改写类型规则

叶子章节只有四种真实策略：

### 5.1 全部搬用 `copy`

判定必须同时满足：

1. 采用一个旧章节或一个连续完整旧章节范围；
2. 主要正文完整使用；
3. 不改变主结构；
4. 不新增实质内容；
5. 仅允许格式整理和安全替换；
6. 旧项目污染检查通过。

### 5.2 简单修改 `light_edit`

典型条件：

- 一个旧章节是主体；
- 替换项目名称、年份、地点、范围、少量参数；
- 删除少量不适用内容；
- 补充少量新招标或 Web 材料；
- 不改变整体结构。

### 5.3 理解重组 `restructure`

满足任一：

- 使用多个旧章节；
- 同一旧章节被拆到多个新内容块；
- 多来源合并；
- 明显调整顺序；
- 合并重复；
- 从旧章节中抽取不同主题后重构；
- 新目录层级与旧目录明显不同。

### 5.4 重新编写 `new_write`

- 没有使用旧投标书正文；
- 主要依据新招标、项目资料和搜索证据；
- 旧标书最多只作为“不可传给 Writer 的结构参考”。

### 5.5 混合处理 `mixed`

`mixed` 不是第五种叶子策略，只是父节点 UI 汇总：

```text
子节点类型集合数量 > 1 → mixed
全部子节点同类型 → 父节点显示该类型
父节点本身也写正文 → 以自身 plan type 和子节点汇总规则计算
```

## 6. 类型动态重算

改写类型不能在目录阶段永久写死。

示例：

```text
原规划：
旧 2.1.2 整章 → 新 2.1.2
类型：全部搬用

用户补充：
增加最新政策原文，要求补充年度变化

重新计算：
类型：简单修改
```

每次下列操作后必须重算：

- 添加/删除旧段落；
- 添加/删除 Web 来源；
- 修改 binding 用途；
- 调整内容块；
- 更换主体来源；
- 修改“保留/删除/补充”指令；
- 规划重新生成。

## 7. 项目级状态机

建议工作空间派生状态：

```text
CREATED
INPUTS_UPLOADING
INPUTS_READY
SOURCE_INDEX_READY
LEGACY_INDEX_BUILDING        # 仅 bid_rewrite
LEGACY_INDEX_READY           # 仅 bid_rewrite
GLOBAL_PLANNING
GLOBAL_PLAN_WAITING_H1
GLOBAL_PLAN_CONFIRMED
WORKSPACE_READY
CHAPTERS_IN_PROGRESS
DOCUMENT_READY
EXPORTED
BLOCKED
```

这些状态应从已有 Artifact、operation 和章节状态派生，不另建一套随手维护的字符串。

---

## 8. 章节规划状态机

```text
MISSING
  ↓ build
BUILDING
  ├─ success → DRAFT
  └─ failure → FAILED

DRAFT
  ├─ edit/search/refresh → DRAFT(new revision)
  ├─ confirm → CONFIRMED
  └─ dependency changed → STALE

CONFIRMED
  ├─ start writing → WRITING
  ├─ plan edited → DRAFT(new revision)
  └─ dependency changed → STALE

STALE
  ├─ rebuild → BUILDING
  ├─ keep old for inspection
  └─ cannot start new write

FAILED
  ├─ retry → BUILDING
  └─ keep diagnostic
```

持久化状态可以只存：

```text
draft
confirmed
stale
failed
```

`missing` 和 `building` 可由是否有记录、operation 状态派生。

---

## 9. 正文状态机与规划绑定

```text
NO_DRAFT
  ↓ confirmed plan + start
WRITING
  ├─ success → DRAFT_READY
  ├─ cancel → NO_DRAFT / previous draft remains
  ├─ failure → WRITE_FAILED
  └─ plan gap → PLAN_REVISION_REQUIRED

DRAFT_READY
  ├─ user edit → DRAFT_READY(new content revision)
  ├─ confirm → CONFIRMED
  ├─ rewrite with same plan → WRITING
  └─ plan changed → DRAFT_STALE

CONFIRMED
  ├─ unconfirm/edit according to existing policy
  └─ upstream dependency changed → FORMAL_STALE

DRAFT_STALE
  ├─ retain for comparison
  ├─ regenerate from new confirmed plan
  └─ cannot silently become formal
```

正文 revision 必须保存其来源：

```text
plan_revision
plan_hash
plan_approval_receipt_id
writer_bundle_hash
```

## 10. 规划确认规则

### human_review

- 用户显式点击“确认编写规划”；
- 服务端重新读取当前 plan；
- 验证 expected revision、plan hash 和依赖；
- 生成用户确认回执；
- 进入 `CONFIRMED`；
- 不自动立刻写正文，用户再点击“开始编写”。

### delegate_review

- Agent 只能给出审核结论；
- Service 执行确定性检查；
- 生成 `delegated` 回执；
- UI 明确显示“由 Agent 代审”；
- 仍受 revision/hash/依赖约束。

### full_authority

- 系统可自动生成 `auto_approved` 回执；
- 但默认仍只完成规划确认，不自动批量写整本；
- 是否允许自动开始当前章节，应作为独立设置，默认关闭；
- 不能因为叫“完全权限”就绕过所有审计，人类给功能起名时很有气势，数据库并不因此更安全。

## 11. 目录融合业务规则

1. 新招标要求与评分项拥有内容主权。
2. 旧目录仅提供候选结构和颗粒度。
3. 严格模板模式下，旧目录不能修改模板固定标题、层级和顺序。
4. 自动目录模式下，可以参考旧目录的子树。
5. 每个新节点必须仍满足现有 ScoreResponseUnit 主责唯一性。
6. `outline_lineage` 必须记录旧节点来源及处理动作。
7. 旧目录中无关节点必须可忽略，不能为了“复用率”硬塞。
8. 新招标中新要求必须新增节点或绑定现有节点。
9. 用户修改目录后，lineage 更新但旧 source ID 不丢失。
10. H1 确认后，目录 revision 变化会使相关章节规划陈旧。

## 12. 来源业务规则

### 12.1 Web 来源

- 搜索结果摘要只做候选。
- 必须获取页面原文或合法可验证的正文快照。
- 来源卡片显示：标题、域名、日期、摘要、计划用途、获取状态。
- 未获取原文的来源不能进入 Writer。
- 过期、冲突或低可信来源应标记风险。
- 搜索结果不得自动成为全局项目事实。

### 12.2 旧投标书来源

- 使用 canonical `SourceBlock.block_id`。
- 显示旧文档、完整标题路径、章节编号、段落范围和正文预览。
- 用户可选择整章或部分段落。
- 不能让 UI 保存页码+索引作为唯一身份。
- 原文不可直接编辑；用户编辑的是使用指令和目标内容块。

### 12.3 项目事实

- 来源于 `ProjectModel`、全局项目上下文和用户确认资料。
- 事实变更按依赖精确使计划陈旧。
- 旧投标书中的项目名、工期等不能进入这一类。

## 13. 陈旧传播规则

| 上游变化 | 影响 |
|---|---|
| ChapterBlueprint revision/hash 变化 | 对应章节及其子树计划 stale |
| 当前章节上下文变化 | 当前章节 plan stale |
| 全局项目事实变化 | 引用了变化事实的 plan stale |
| 旧投标书输入被替换 | 引用其 block_id 的 plan stale |
| Web evidence snapshot 被废止 | 引用该 evidence 的 plan stale |
| 计划 draft 变化 | 基于旧 plan 的正文标记 stale |
| 仅聊天历史变化 | 不影响 plan |
| 权限模式变化 | 不影响内容，但影响下次确认方式 |
| 无关章节正文变化 | 默认不影响当前 plan；仅显式 sibling dependency 才影响 |
| 目录显示编号重算但 chapter_id/职责不变 | 仅 UI 编号更新；是否 stale 由 Blueprint hash 策略决定 |

## 14. 错误恢复规则

### 规划生成失败

- 保留上一个有效规划；
- 展示本次 operation 的错误；
- 允许重试、减少搜索范围或改用已有材料；
- 不清空正文。

### 搜索失败

- 已成功获取的来源保留；
- 失败来源标记；
- 用户可确认“仅使用现有资料”，但必须显式记录；
- blocking 缺口未处理时不能确认。

### 写作失败

- 不提交半成品正式 revision；
- 流式临时内容可作为诊断预览，不冒充草稿；
- 允许使用同一个 plan revision 重试；
- 若失败原因是资料缺口，返回规划修订，不无限重试 Writer。

### 并发冲突

- 服务端返回最新 revision/hash；
- 前端保留用户未提交编辑；
- 提供“重新加载并合并”；
- 不自动覆盖别人已经确认的规划。

### 服务重启

- build/write operation 有持久状态；
- 重启后识别 running 但 lease 失效的任务；
- 标为 interrupted 或按现有 batch 机制恢复；
- 幂等键避免重复生成。

## 15. 最终导出规则

导出只使用：

```text
chapter.title
formal chapter content
document structure
```

不得导出：

```text
【全部搬用】
【简单修改】
【理解重组】
【重新编写】
【混合处理】
source card
binding instruction
plan status
旧投标书路径
内部评分 ID
```

工作台显示标题使用：

```text
display_title = chapter_number + title + rewrite_type_badge
```

正式导出使用：

```text
export_title = chapter_number + title
```
