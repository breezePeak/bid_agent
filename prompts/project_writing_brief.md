# 默认项目写作要求

本要求沉淀真实标书编制中的有效做法，只规定“怎么写”，不得替代招标文件，也不得作为公司事实或履约证据。

## 先研究，再成稿

先识别项目背景、范围、任务、评分点、成果和验收要求。资料不足时，可用外部参考资料补充政策背景、技术标准、行业术语、成熟方法和成果样式。外部资料与招标要求冲突时以招标文件为准，不能确认的参数、数量、周期和标准版本不得自行补写。

## 项目理解结构

“工作任务理解”优先按三个方面组织：

1. 项目背景：说明招标文件中的直接背景，并结合有依据的政策、行业和业务背景解释项目为何实施、解决什么问题。
2. 项目范围：写清工作区域、对象、数据范围、业务边界、时间边界和不属于本项目的内容。
3. 具体工作任务：把采购需求拆成可执行任务，建立任务、方法、成果和验收要求之间的对应关系。

背景扩展必须与项目直接相关，不堆砌宏观政策。

## 技术方案可用性

每项核心技术任务应尽量形成闭环：

输入资料 → 预处理 → 判定规则/关键参数 → 分步作业 → 过程质检 → 异常处置 → 阶段成果 → 最终成果 → 验收对应。

技术路线先用一段话概括总体链路，再分项展开。分项方案不能停留在“严格按照要求执行”“确保质量”等原则性表态。

涉及分类、解译、核查、巡检、测试或验收时，优先给出可直接使用的结构化表格，例如分类/解译标志表、属性字段表、任务成果表和质量检查表。字段、代码、阈值和分类必须有依据；无依据时只描述机制，不虚构数值。

## 证据边界

1. 招标文件确认采购要求、范围、参数、成果和合同约束。
2. 公司资料确认投标人的资质、人员、设备、证书、业绩和既有能力。
3. 外部参考资料只支持背景、政策、标准、术语、技术方法和行业实践。
4. 外部资料中的相似案例不得改写为“我公司已具备”或“我公司曾完成”。
5. 需要补证的资格和商务内容保留结构化材料缺口，不使用“XXX”“待填写”等终稿残留占位符。

## 成稿检查

- 是否逐项覆盖评分点和招标任务；
- 是否存在只复述要求、没有实施方法的章节；
- 是否形成任务—方法—成果—验收闭环；
- 是否把外部参考误写成公司事实；
- 是否存在无来源的数字、标准版本、人员、设备、案例或承诺；
- 专业表格能否直接指导后续编制和实施；
- 章节之间是否重复、矛盾或口径不一致。
